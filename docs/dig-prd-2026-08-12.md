## 1. What Dig is

Dig lets someone manage their Spotify playlists by talking to Claude. Create a playlist, clean up an existing one, reorder it, strip duplicates, or say "this playlist is late-night dub, find me fifteen more like it" and have Claude actually dig up the tracks.

It ships as a Claude Code plugin. Each person installs it themselves, connects their own Spotify account, and their data never touches anyone else's machine.

**The one-line version:** a record-store clerk who knows your taste and has your library memorized.

## 2. Who it's for

Tony's friends. People who care about music, use Claude, and are not developers. They should never see a terminal, edit a config file, or understand what an MCP server is.

This constraint drives most of the decisions below. If a step requires explaining what a JSON file is, the step is wrong.

## 3. What a user must have — the Premium requirement

**Dig requires a Spotify Premium subscription. There is no workaround, and no free-tier path.**

This is not Dig's choice. As of February 2026, Spotify requires the owner of a developer app to hold Premium for that app to function at all — including for reading your own playlist. Since every Dig user registers their own app, every Dig user is an app owner.

Spotify's own error text: *"Active premium subscription required for the owner of the app."*

### Making it unmissable

We cannot check this programmatically. Spotify removed subscription status from its user endpoint in the same migration. So the requirement gets stated in **five** places, before and after the fact:

1. **The GitHub README**, in the first paragraph, above the install instructions.
2. **The marketplace description**, so it appears in the plugin browser before anyone installs.
3. **The plugin's own description**, visible in the install confirmation.
4. **Step 0 of the setup walkthrough**, before the user is asked to do anything at all. Ask outright: "Do you have Spotify Premium? If not, stop here — Dig can't work without it, and that's Spotify's rule, not ours."
5. **Runtime**, by detecting Spotify's specific Premium error and translating it, rather than surfacing a raw 403.

Requirement 4 matters most. Sending someone through app registration only to fail at the end is the worst version of this.

### The other two hard limits

- **Dig only works on playlists the user owns or collaborates on.** Reading a friend's playlist, or any Spotify editorial playlist like Discover Weekly, is no longer possible for a new app. Say this in the README so nobody is surprised.
- **The connection expires after six months** and must be renewed. Spotify made this absolute in June 2026, and refreshing does not extend it. Dig warns at five months and gives a one-step reconnect.

## 4. What Dig does

**Playlists, at full depth. Nothing else.**

| In scope | Notes |
|---|---|
| Create, rename, re-describe playlists | Public/private/collaborative |
| Add tracks | Verified before adding, see §6 |
| Remove tracks | Two-step confirm, see §7 |
| Reorder | Including arbitrary reordering, not just single moves |
| Find within a playlist | Spotify has no way to do this; Dig builds it |
| Deduplicate | With the position caveat in §7 |
| Compare two playlists | What's in one and not the other |
| Grow a playlist by feel | The signature feature, see §5 |
| Cover art | **Cut from v1** — planned for v1.1, decided 2026-08-14 |

**Explicitly not in scope:**

- **Playback.** No play, pause, skip, queue, or device control. This is a curation tool, not a remote.
- **Library management.** No saved albums, no followed artists.
- **Other people's playlists.** Not a choice; Spotify closed it.
- **Anything outside Spotify.** No Apple Music, no cross-service transfer.
- **Claude Radio.** Stays exactly as it is, its own local repo, untouched, permanently separate. Decided 2026-08-14: Dig will NOT be rebuilt under it.

## 5. The signature feature: digging

The reason to use Dig instead of Spotify's own app.

The user says something like "this playlist is late-night dub, give me fifteen more" or "more like tracks 4 through 9, less like the rest." Claude proposes actual tracks from its own knowledge of music. Dig searches Spotify for each one, confirms it found the right recording, and adds only the ones that check out. Anything uncertain comes back to the user rather than being added quietly.

**Spotify's recommendation engine is not available to us** — it was closed to new apps in November 2024. That turns out to be the interesting part. Claude proposing tracks it actually knows about, with Dig verifying each one exists, is a better experience than an algorithm, and it is a thing no other Spotify tool does.

**Design rules:**

- Claude proposes. Dig verifies. Dig never invents a track.
- Present the list before adding, with what was found and what wasn't.
- Report misses honestly. "Nine of fifteen are on Spotify" is a fine answer.
- Never pad the list to hit a number.

## 6. Getting the right track

The verification rules are settled and implemented. Full algorithm and a 31-case test suite live in `dig-matching-reference.py`.

The short version: a proposed track is only added when the artist matches, the title matches with **every meaningful word accounted for on both sides**, and the version class agrees — a live recording is not a studio recording, a remix is not the original, and a re-recording is not the first cut. Duration corroborates when known.

Three rules that matter at the product level:

1. **Never auto-add an uncertain match.** A missing track costs the user one message. A wrong track in a curated playlist is a silent corruption they may not notice for weeks. Bias hard toward omission.
2. **When uncertain, say why in plain words** and offer the alternatives, so the user can decide rather than re-litigate.
3. **Honor an explicit request for a version.** If someone asks for the live version, they get the live version. The rule is that versions must *agree*, not that non-studio versions are rejected.

## 7. Destructive operations

Spotify has no undo. Removing tracks is permanent, and its 90-day recovery covers deleted playlists but **not** tracks removed from a surviving one.

**Every destructive operation is two steps.** Dig first returns a plan: what would be removed, how many, a sample, and a one-sentence summary. Only after the user approves does anything happen. The approval prompt shows the human summary, not a technical payload.

**Additional rules:**

- **Snapshot the playlist to disk before every destructive write**, and offer a restore.
- **Verify after every write.** Spotify can return success and change nothing. Re-read and confirm the change landed. If it didn't, say so.
- **No replace-all tool.** Passing an empty list to Spotify's replace endpoint silently empties a playlist. No user request needs that as a single action.
- **Unfollowing a playlist is off by default.** For the owner it is effectively deletion.

**One limitation to state plainly in the product:** Spotify removed the ability to delete a single copy of a duplicated track in 2024. Dig can only remove all copies and re-add one, which moves it to the end of the playlist. Dig must say this before doing it, not after.

## 8. How it ships

**A Claude Code plugin, distributed from its own GitHub repository. Tony hosts nothing.**

```
/plugin marketplace add line7works/dig
/plugin install dig@dig
```

Then Claude Code prompts for the Spotify Client ID and the setup walkthrough takes over.

**Contents:** an MCP server for the Spotify mechanics, a setup skill for onboarding, and a digging skill carrying the taste and judgment.

**Requirements on the user's side:** they run Claude Code, most likely inside the Claude desktop app. Plugins are a Claude Code feature, not a plain-chat feature, and this will not work in Claude Code on the web.

**Repository:** standalone, not inside a Line 7 repo. Branded as a Line 7 product — "brought to you by Line 7" — with the specifics to be settled later.

**Possible later step:** submission to Anthropic's community marketplace, which would make it a one-line install for anyone. Not a launch requirement.

## 9. Onboarding

The hardest part of this product is not the tool. It is the ten minutes before the tool works.

**Order of operations:**

0. **Premium check.** Ask first. Stop here if the answer is no.
1. Create a Spotify developer app. Free, roughly two minutes.
2. Paste in the redirect address Dig provides, exactly.
3. Copy the Client ID back into Claude.
4. **Add themselves under User Management.** Their own app rejects them until they do.
5. Sign in through the browser.

**Two pieces support this:**

**A local reference page.** Dig already runs a small local web server to catch the Spotify sign-in, so serving a page from it is nearly free. It is **read-only** — the whole picture at once, real links, the redirect address available to copy, Line 7 branding. Nothing is typed into it and it captures nothing.

**A setup skill.** Claude walks the user through conversationally, one step at a time, in their own chat, and points them at the page for the visual.

**Rules for the walkthrough:**

- It carries **exact URLs and exact button names**, verified against the dashboard as it looks today. A vague skill means Claude fills gaps by guessing, and a confidently wrong instruction is worse for a non-technical person than no instruction.
- **Step 4 gets stated loudly and repeated.** It is the step that breaks most people, and its only symptom is a permission error that looks like something else entirely. It also takes up to fifteen minutes to take effect, which must be said out loud or people will assume it failed.
- **The word `localhost` appears nowhere in the project.** Spotify rejects it, and stale examples containing it are a documented cause of failed setups in other tools.
- **Say "never paste your Client Secret."** It sits directly beneath the Client ID on the dashboard and looks identical. Dig never needs it.
- **No screenshots of Spotify's dashboard.** They go stale the moment a button moves, and a stale screenshot misleads more than plain text.

## 10. Errors are instructions

Every error message names the cause and the next action, in plain language. No raw Spotify errors reach the user — a permission error on one endpoint means something entirely different from the same error on another, and Spotify's own message for a retired endpoint sends people chasing the wrong problem for days.

Draft copy for the six most likely first-run failures is in the research document.

**A self-check command** (`/dig-doctor` or similar) verifies the Client ID, the allowlist, Premium, token freshness, and one live call. When Spotify changes something — and it will — the user gets a diagnosis instead of a mystery.

## 11. Technical decisions

Recorded here so they are not relitigated. Reasoning is in the research document.

| Decision | Choice |
|---|---|
| Language | Node. It is the only path where dependencies install with no terminal step. |
| Spotify auth | PKCE, Client ID only, no client secret ever. |
| Credentials | Each user's own Spotify app. Nothing of theirs touches Tony. |
| Hosting | None. |
| Spotify SDK | None. Call the REST API directly; every wrapper lags Spotify's changes by months. |
| Client ID capture | The plugin's own configuration prompt. Not marked `required`, not marked `sensitive` — both trip live bugs that break the install silently. |
| Token storage | The plugin's persistent data directory, created locked-down, never in the repo, never derived from the working directory. |
| Access token | Held in memory only, never written to disk. |
| Logging | Everything to stderr. A single stdout write breaks the protocol. |
| Tool count | 12 to 16. |

## 12. Open questions

### Resolved 2026-08-15

1. **Does a plugin's MCP server actually start inside the Claude Code desktop app? YES — verified live.** A zero-dependency hello-world plugin (`~/Developer/dig-plugin-test`, installed at user scope via the terminal CLI) started its MCP server and answered a tool call inside the desktop app on Tony's Mac Studio (node v22.14.0, plugin resolved from the marketplace cache, `CLAUDE_PLUGIN_ROOT` set correctly). The open bug report does not reproduce here. **One caveat discovered:** the desktop app cannot run `/plugin` — install commands are terminal-only ("Some commands only work in the Claude Code terminal"), and a user-scope install from the terminal is what the desktop app then loads. **However, the no-terminal install path is verified end-to-end (2026-08-15):** the friend never opens Terminal. Claude inside a desktop-app session can run the `claude plugin marketplace add` / `claude plugin install` CLI itself via its own shell tool — tested live: it inspected the plugin, installed it at user scope, and the tool answered in the next session. One walkthrough requirement this surfaced: **plugin MCP servers connect at session startup, so after install the user must start a new chat before the tools exist.** The walkthrough's install step is therefore: paste one sentence ("Install the Dig plugin from <repo>"), approve the prompts, start a new chat.

### Resolved 2026-08-14

2. **Branding:** minimal for now — a plain "Dig — a Line 7 product" footer line on the reference page and README, no logo. Real branding waits until Line 7 Tools branding is settled overall.
3. **Repository is public from day one.** Docs and the Premium warnings must be airtight before launch, since strangers can install it immediately.
4. **Cover art is cut from v1** (moved to v1.1).
5. **Claude Radio stays separate, permanently.** Its script does not get rebuilt on top of Dig.

## 13. What "done" looks like

A friend who does not code can go from never having heard of Dig to a working playlist edit in under fifteen minutes, without opening a terminal, without editing a file, and without asking Tony for help.

Anything that breaks that sentence is a bug, including a confusing error message.
